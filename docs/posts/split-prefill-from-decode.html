Disaggregation should be judged by the cache it moves

Disaggregated serving should be judged by the KV cache it moves across the network, not by the throughput multiplier in its headline.

The common view is that disaggregated serving, which runs prefill and decode on separate pools of hardware, is a niche for very large deployments. I think that is close to backwards. Splitting the two phases is the first step toward running inference like a distributed database, and agent workloads, with long contexts, short answers and repeated prefixes, will push the idea much further than chat did. The split also has a cost that most published tables leave out. The cache has to cross a network between prefill and decode, and that transfer is the part of the design I would argue hardest about.

Each request is two jobs run back to back on the same GPU. Prefill reads the whole prompt at once, which becomes large matrix multiplications that keep the arithmetic units busy. Decode writes the answer one token per step, and each step streams the model weights and the stored keys and values through memory. Leviathan et al., 2023 state the serial part plainly: "decoding K tokens takes K serial runs of the model." Prefill is therefore limited mostly by arithmetic and decode mostly by memory traffic. On one device the two share a queue. A long prompt admitted into a batch of decoding users takes a slice of the device, and those users feel it as a pause between their tokens.

That mechanism is what Zhong et al., 2024 build around. DistServe optimizes for goodput, meaning requests that meet their latency targets, rather than raw throughput. They report that it can serve "7.4x more requests or 12.6x tighter SLO, compared to state-of-the-art systems," while "staying within latency constraints for > 90% of requests." The choice of metric is most of the argument. Raw throughput can look healthy while a tail of users waits behind somebody else's prompt.

The colocated alternative deserves its due. Keep one pool and one scheduler, and tune it hard by capping prompt length, reordering the queue and managing memory. Kwon et al., 2023 report that vLLM "improves the throughput of popular LLMs by 2-4x with the same level of latency," and a large part of that comes from managing the KV cache so little memory is wasted. Better paging is a real gain. It does not give prefill its own arithmetic, and it does not stop a compute-heavy burst from landing inside a memory-heavy loop. Colocation can be tuned a long way, but eventually the two phases' bottlenecks collide, and that is where I think the split starts to pay.

The first thing I would change is the product spec, before anyone picks a topology. Time to first token and time per output token are different promises to different users. A coding agent waiting on its next step cares about the first token. A streamed answer cares about a steady rhythm once it starts. Once those two numbers are written for each product surface, the disaggregation decision becomes a calculation: split where the colocated system misses the targets during the bursts that matter. The mechanism is that a goodput scheduler can only trade one user's latency against another's if someone has said whose latency counts. The failure is that targets written in advance can be set loosely enough that a team passes its own dashboard. What would convince me is a plot of the targets against real traffic, showing the colocated system missing them at the peaks. Without that plot, the SLO is a number chosen to justify the design.

Agent traffic is more prefill-heavy than chat was. Each turn resends a long prefix, most of it already seen, and appends a short step, so prefill dominates the work per request while the cache built by earlier turns gets reused. I would size the two pools from the token mix of real traffic: prompt tokens against output tokens, and the reuse rate of prefixes. The ratio should come from the trace, not from a reference architecture. Placement matters as much as sizing. Qin et al., 2024 frame Mooncake around a KVCache-centric design, which changes the question from which GPU runs this request to where the request's prefix already lives. That is a placement and eviction problem with bandwidth limits, and the scheduler has to solve it on every turn. The failure mode is that agent traces change shape quickly, so a ratio tuned this month can be wrong the next. What would convince me is a replay of recent agent traces against the planned split, reporting prefill and decode utilization separately. If one pool idles while the other queues, the ratio is wrong whatever the diagram says.

There is a strong objection, and it can reverse the design. Moving a cache costs time, and for a short prompt the transfer can take longer than recomputing the prefill on the decode machine. The break-even depends on how big the cache is, and the model architecture sets that size. DeepSeek-AI, 2024 report that their attention design "reduces the KV cache by 93.3%" compared with DeepSeek 67B. If the cache is 6.7 percent of its former size, the handoff is about fifteen times smaller (100 divided by 6.7, derived). A choice made in the model layers therefore changes whether the split pays. A team running a model with a large cache over a slow link should expect the transfer to dominate, and I would measure that before reading any multiplier. Disaggregation is also not free at small scale. Two pools need their own provisioning, a router that knows where each cache lives, and enough load to keep both busy. A single GPU serving a handful of users should stay colocated.

Vendors push in the other direction. NVIDIA, 2025 says Dynamo boosts "the number of requests served by up to 30x" when running DeepSeek-R1 on Blackwell, and separately that it "more than doubled the throughput performance" when serving Llama 70B on Hopper. Treat both as vendor claims. The academic numbers have the same problem. Patel et al., 2023 say phase splitting can deliver "1.4x higher throughput at 20% lower cost than current designs," and separately "2.35x more throughput with the same cost and power budgets." Those are two points on one cost curve. One spends the gain on cheaper hardware and the other on more tokens from the same machines, so a team that reads only the 2.35 buys a different cluster than one that reads only the 1.4. I would require every multiplier to come with its baseline, its SLO and its unit. The NVIDIA product page labels the 30x as tokens per second per GPU, while the blog calls it requests served, which is exactly the habit that needs to end.

The chart is the thing I would not show without its note. Each bar is a best case from a different setup, and the Dynamo bar is a vendor's best case on the newest hardware. Read side by side, the bars suggest a ranking that the sources never measured. The honest version of a headline names the workload, the latency target and the cost per token, and most published tables give only the first two.

Prefill and decode can share one GPU for years without anyone asking what crosses between them. Once they run on separate machines, every request's cache has to cross the gap, and in most architecture diagrams that arrow is the thinnest line on the page. I would start every architecture review by asking how many bytes that arrow carries per request.
